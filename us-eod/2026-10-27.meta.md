## Source health

- **MCP layer absent.** `mcp__tradingview_advanced__*` and `mcp__yahoo_finance__*` are not registered in
  this Cloud session (tool search returned 0 hits), so the skill's MCP path was never attempted and no
  MCP failure was raised. The equivalent public HTTP endpoints were used instead.
- **Yahoo was throttled at the start of the run.** `query1/query2.finance.yahoo.com` returned
  `HTTP 429 Too Many Requests` for spark and chart from the window check until roughly 16:20 ET. During
  that window `api.nasdaq.com` was used as the reference close; it recovered once Yahoo did and was then
  kept for independent verification and for class-aware market caps.
- **TradingView screener healthy.** All 17 region calls returned HTTP 200 with `len(data) == totalCount`,
  i.e. a complete, gap-free universe for every region.
- **Transport:** verified TLS through the sandbox CA (`--cacert`); no `-k`. The egress proxy leaf
  certificate was valid for the whole run.

## Why the US file does not use the screener close

The TradingView US feed is a 900-second delayed stream, and it was still behind when the window opened
at 16:01 ET. Measured against the official 16:00 ET closing print:

| Metric (5,554 US rows that traded today) | Value |
|---|---:|
| Median close gap, screener vs official | 0.000% |
| Mean absolute close gap | 0.425% |
| Maximum absolute close gap | 13.741% |
| Rows where the screener close was off by more than 0.5% | 20.4% |
| Session volume: screener vs official (median) | +23.8% |
| Day high: screener vs official (rows off by >0.05%) | 20.1% |

On a large-cap sample the screener close even flipped the sign of the day's move (PLTR: +0.59% on the
screener versus −0.12% at the official close), so the US file takes the price bar from Yahoo and keeps
the screener for the fields only it publishes.

| US field | Source | Notes |
|---|---|---|
| open | TradingView | The 09:30 print is far inside the delayed window. Yahoo's spark does not publish an open. |
| high, low | Yahoo | Official session range; matched Yahoo's own 1-minute bar extremes exactly on a 24-name check, where the screener range was marginally wider. |
| close | Yahoo | `regularMarketPrice`, stamped 16:00:0x ET — the official closing print. |
| volume | Yahoo | `regularMarketVolume`, the official session volume. |
| change_pct | derived | `(close − chartPreviousClose) / chartPreviousClose`. The screener's own prior close reproduced Yahoo's `chartPreviousClose` exactly on 48/48 names. |
| market_cap | TradingView, rescaled | Screener cap × (official close ÷ screener close), so the cap matches the price in the same row. |
| market_cap (preferreds) | Nasdaq or empty | 234 rows whose screener cap is a company-level cap shared with other listings (bank and utility preferreds) get a class-aware Nasdaq cap where one exists, otherwise the cell is left empty rather than carrying a wrong number. |
| pe_ratio, sector | TradingView | Only source available. |

Coverage on the US file: **5716 of 5716 rows carry the official Yahoo close**, 0 rows fall back to the
screener close. **162 rows had no session on 2026-10-27** (halted or not-yet-traded names) and their session
fields — open, high, low, close, volume, change_pct — are left empty rather than carrying an earlier
session's price. Their tickers are listed in `data/_us_detail.json`.

## Method and limitations

- **US universe = US-venue listed** (`type=stock`, OTC excluded): 5716 rows, of which 1,012 are
  foreign-issuer listings (Canada 220, China 128, Israel 91, Hong Kong 87, Singapore 77, Bermuda 58,
  UK 53). The issuer country is kept in the pull but is not a filter, matching the archive convention
  of prior days (5,714–5,716 rows).
- **Venue collapse (international only).** One row per company per region, keyed on the normalised company
  name, preferring the primary listing venue (XETR for Germany, TSX for Canada, TSE for Japan, TWSE for
  Taiwan); a ticker listed on two venues of the same country is also collapsed to the primary venue.
  The US is deliberately *not* collapsed so share classes survive. Germany collapses hardest (4,281 raw
  → 497 rows); Canada 4,256 → 2,673; Japan 3,892 → 3,858; Taiwan 2,331 → 2,330.
- **Cross-listed securities appear in more than one file** (for example a German-primary name also
  trading in Amsterdam) with each file's own close time. No cross-region dedupe is performed.
- **`market_cap` is in each row's native currency** (USD, EUR, JPY, TWD, CAD, AUD, GBP, DKK, SEK) and is
  not FX-converted, so it is not comparable across regions without conversion. The screener also assigns a
  company-level cap to each share class, which is why the 234 preferred rows are handled as described above.
- **Prices are rounded to 4 significant figures** per the skill. `change_pct` is computed from
  full-precision values before rounding, so it will not reconcile to the cent against the rounded columns.
- **The skill's shibui-finance SQL path (US) is not available in this environment.** The screener returns
  the full schema in one call per region, so no column is lost relative to the skill's note about
  TradingView stripping `volume` / `pe_ratio` / `sector`.
- **A file for this date already existed on the remote?** No — this is the first artifact for 2026-10-27.
